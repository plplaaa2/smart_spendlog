# Add-on 문자 파싱 아키텍처

## 1. 목적

Home Assistant Companion 알림 또는 Webhook으로 전달된 문자 원문에서 금액, 가맹점, 거래일시, 결제수단, 거래 유형과 부가 정보를 추출해 거래 레코드로 변환한다.

## 2. 진입점

문자 파싱의 공개 진입점은 `account_book/parser.js`이다.

- `parseNotification`: 규칙 기반 파싱
- `parseNotificationWithAI`: 규칙 기반 파싱 실패 시 선택적으로 사용하는 AI 파싱
- `generatePatternFromText`: 문자 원문에서 규칙 패턴 생성
- `generatePatternWithAI`: AI 기반 규칙 생성
- `sanitizePattern`: 저장된 패턴의 정규식 안전성 보정

## 3. 전체 처리 흐름

```text
알림 / Webhook 입력
        |
        v
원문 정규화 및 notification_logs 기록
        |
        v
사용자·기본 규칙을 순서대로 정규식 매칭
        |
   +----+----+
   |         |
 성공       실패
   |         |
   v         v
필드 추출   AI 파싱(선택)
   |         |
   +----+----+
        v
금액·일시·결제수단·거래유형 보정
        |
        v
중복 검사 및 transactions 저장
        |
        v
분석·HA 센서·응답·알림 갱신
```

## 4. 규칙 기반 파싱 단계

### 4.1 원문 정규화

`text_parser.js`는 제어용 유니코드 문자와 Windows 줄바꿈을 정리한 뒤 규칙을 적용한다. 원문 자체는 추적과 재처리를 위해 로그에 보존한다.

### 4.2 규칙 매칭

각 규칙의 `pattern`을 정규식으로 컴파일하고, 첫 번째로 유효하게 매칭되는 규칙을 사용한다. 규칙은 다음 명명 캡처 그룹을 사용할 수 있다.

| 그룹 | 의미 |
|---|---|
| `amount` | 거래 금액 |
| `merchant` 또는 `usage` | 가맹점·사용처 |
| `time`, `datetime`, `date` | 거래일시 |
| `payMethod`, `pay_method` | 결제수단 |
| `payType`, `pay_type` | 결제 유형 |
| `used_point` | 사용 포인트 |
| `account`, `balance`, `cumulative` | 계좌·잔액·누적 부가정보 |
| `status`, `type_text` | 입금·출금·취소 상태 |

금액이 없거나 숫자로 변환되지 않는 매칭은 실패로 처리하고 다음 규칙을 시도한다. 날짜·시간 영역 안에서 금액이 매칭된 경우에는 잘못된 금액 추출을 방지하기 위해 해당 규칙을 건너뛴다.

### 4.3 금액과 통화

- 쉼표를 제거한 정수 금액은 원화 거래로 처리한다.
- `$` 또는 `USD`가 있으면 `original_amount`와 `currency = USD`를 기록한다.
- 현재 구현은 USD 금액을 임시 환율로 원화 환산하므로, 환율 설정·외부 환율 조회·최종 보정 흐름을 별도 검증해야 한다.

### 4.4 가맹점과 날짜

가맹점은 공백·불필요한 접미어를 정리하고 브랜드 매핑을 적용한다. 날짜는 `parseFlexibleDatetime`을 사용해 다음 형태를 지원한다.

- 연도가 포함된 날짜와 시각
- 연도 없는 월·일과 시각
- 오전·오후 및 AM/PM
- 숫자로 연결된 날짜·시각 형식

날짜를 추출하지 못하면 Webhook의 fallback 시각을 우선 사용하고, 없으면 서버 현재 시각을 사용한다.

## 5. 결제수단과 거래유형 결정

결제수단은 규칙 캡처값, 규칙 설정값, 원문 키워드 순서로 보완한다. 결제 유형은 다음 내부 값으로 정규화한다.

- `CREDIT`
- `CHECK`
- `TRANSFER`
- `CASH`

거래 유형은 `transaction_classifier.js`가 원문·상태 캡처값·규칙 기본값을 함께 판단한다.

- 입금·수입 표현: `INCOME`
- 출금·결제·사용 표현: `EXPENSE`
- 취소·환불은 원 거래 성격에 따라 반대 방향으로 보정하고 메모를 추가한다.
- 판단 근거가 부족하면 규칙의 기본 유형을 사용한다.

## 6. AI fallback

규칙 기반 파싱이 실패하거나 설정상 AI 보정을 사용하는 경우 `ai_parser.js`가 호출된다. AI 결과도 저장 전에 금액·필수 필드·형식을 검증해야 하며, AI 장애나 불완전한 응답은 로컬 파싱 및 거래 저장을 중단시키지 않아야 한다.

## 7. 저장과 실패 처리

`routes/webhook.js`의 처리 코어는 다음 결과를 관리한다.

- 원문과 제목을 `notification_logs`에 기록
- 성공한 파싱 결과를 `transactions`에 저장
- 매칭 규칙 ID와 파싱 상태를 기록
- 중복 거래는 `IGNORED_DUPLICATE`로 표시
- 실패한 원문은 삭제하지 않고 재분석 가능한 상태로 보존

알림이 짧은 시간에 연속으로 들어올 수 있으므로 Webhook 처리에는 순차 큐가 사용된다. 큐 처리 실패는 해당 작업의 오류로 기록하고 이후 작업 처리를 계속할 수 있어야 한다.

## 8. 테스트 기준

파서 변경 시 최소한 다음 케이스를 검증한다.

- 일반 카드 승인
- 체크카드·은행 이체
- 입금과 출금
- 취소·환불
- USD 금액과 환율 보정
- 날짜 없는 문자와 날짜 형식이 다른 문자
- 포인트 사용·잔액 포함 문자
- 동일 문자 재수신
- 규칙 실패 후 AI fallback 실패

테스트 데이터에는 실제 계좌번호·토큰·개인 식별정보를 사용하지 않는다.

## 9. 유지보수 주의사항

- 규칙의 캡처 그룹 이름을 변경하면 `text_parser.js`와 기본 규칙을 함께 점검한다.
- 파싱 실패 원문을 숨기거나 버리면 규칙 개선이 어려워지므로 로그 보존 정책을 먼저 확인한다.
- 정규식 변경은 금액 캡처 범위와 날짜 영역 오인 매칭을 함께 검증한다.
- 인코딩이 깨진 기존 소스의 정규식은 의미를 추측해 수정하지 말고, 원본 문자 샘플과 테스트를 확보한 뒤 수정한다.
